# Provider adapters

`src/providers/index.ts` exports the interfaces agreed in `docs/interfaces.md`. `createProviders` injects environment, fetch, time, and a small Photon client for offline tests. No adapter changes incident state or authorizes a responder.

## Configuration

| Provider | Environment | Behavior without configuration |
| --- | --- | --- |
| Photon cloud | `SPECTRUM_PROJECT_ID`, `SPECTRUM_PROJECT_SECRET` | Send returns `failed`; listener stays inactive |
| FinchNode | None | Reads only the public synthetic `patient-demo-001` fixture |
| ElevenLabs | `ELEVENLABS_API_KEY`, `ELEVENLABS_VOICE_ID` | Returns no audio |
| OpenAI-compatible model | `LIFELINE_LLM_API_KEY`, `LIFELINE_LLM_BASE_URL`, `LIFELINE_LLM_MODEL` | Uses visibly degraded source templates |

The model base URL is the API prefix, such as `https://provider.example/v1`; the adapter appends `/chat/completions`. Requests require HTTPS, except localhost development. Set server-side API credentials in `.env`.

For local inference, install a compatible [Ollama runtime](https://ollama.com/download/mac), pull [qwen2.5:3b](https://ollama.com/library/qwen2.5:3b), and keep `npm run ai:local` running alongside the backend. The launcher prefers the separately installed native runtime on this development Mac; on another machine it uses `ollama` from PATH, or an explicit `LIFELINE_OLLAMA_BIN`. It binds to this Mac's loopback address and disables cloud inference. Set these private `.env` values, then restart the backend:

```dotenv
LIFELINE_LLM_API_KEY=local-placeholder
LIFELINE_LLM_BASE_URL=http://127.0.0.1:11434/v1
LIFELINE_LLM_MODEL=qwen2.5:3b
```

The local API key value satisfies the adapter's configuration check; [Ollama ignores it](https://docs.ollama.com/api/openai-compatibility). Model download and generation remain separate from sensor monitoring. Use the local question preview to verify generation and citations before rehearsing live responder messages.

Status `configured` means configuration exists, not that a live integration has passed. The detail records lookup/preparation/listener failures. SDK errors, credentials, incoming bodies, and recipient numbers are not copied into status details.

For setup, configure a managed Photon cloud line and the two Spectrum project values; add approved E.164 responders through `LIFELINE_RESPONDERS_JSON`. Confirm an actual incoming text and reaction from those phones. For ElevenLabs, use a key with text-to-speech access and an existing voice ID. A failed preparation returns no clip and remains cached for that process; after fixing configuration, restart to prepare it once. FinchNode needs no credential for the fixed synthetic demo. The AI model needs an API key, an API base URL, and the exact model name; an invalid response visibly falls back to source fields. Check provider detail alongside `configured`; a configured provider can be unavailable.

For the wearer side, set `LIFELINE_WEARER_PHONE` to the approved E.164 phone, distinct from every responder. The iPhone is a communication/check-in companion: it polls incident progress and exposes explicit help/cancel controls, without motion acquisition, microphone capture, speech recognition, or audio playback. A persisted `wearer_checkin` sends the companion iMessage through Photon; `wearer_ack` and `wearer_status` share its wearer worker lane. Queued/failed check-ins stop at escalation or cancellation; a send already submitted may finish later, with its actual outcome recorded. Phase updates notify the wearer without claiming that acceptance establishes departure or safety. The connected stock FREE-WILi supplies acceleration, buttons, display, audio and bounded microphone capture through its official SDK bridge. See [the bridge boundary](../native/freewili/README.md).

Wearer replies require the complete configured phone identity and a current-incident accepted conversation/line binding. Ordinary text in that conversation needs no copied incident code or threaded reply. An explicit stale target cannot be rescued by a newer incident code. During check-in, exact help escalates; positive text queues a persisted `wearer_ack` directing the wearer to WILi's green button. Ambiguous text preserves the deadline. Acknowledgements stop being eligible at cancellation/escalation/the original deadline. Reactions never cancel a check-in. Inbound IDs, audit events, acknowledgements, and state changes commit together.

After escalation, the same private wearer conversation remains open. Updates are persisted as literal `WEARER_REPORT` observations and relayed once to each eligible contacted responder; they refresh the contextual handoff without changing ownership, phase, deadlines or the read-only clinical snapshot. Explicit reply targets must belong to an accepted wearer message for the active incident; closed-incident messages cannot attach to a newer incident. Positive prose after escalation is evidence, never resolution. Full live wearer/responder rehearsal remains a separate check.

## Photon

Use `@spectrum-ts/core@12.10.1` and `@spectrum-ts/imessage@12.10.1`; cloud discovery renews line tokens. [Official cloud setup](https://photon.codes/docs/spectrum-ts/providers/imessage)

The adapter resolves an E.164 user, opens a DM, rechecks the outbox action's current authorization, and sends once. Accepted sends retain native message, chat, and sending-line IDs. Threaded replies use the persisted source inbound ID, chat, and line: resolve that existing space, look up the exact inbound message, verify its sender/channel, then call its native `reply`. A missing or contradictory target fails before submission; there is no DM fallback. On SDK cache misses, the persisted original inbound metadata supplies trusted channel provenance because native reconstruction uses the requested chat hint. Authorization ending during preparation returns `cancelled`. A returned message ID becomes `provider_accepted`, which does not establish recipient delivery. An exception or missing ID after submission returns `unknown`. No adapter retries; the persisted worker owns reconciliation/retry policy. [Official send and DM interfaces](https://photon.codes/docs/spectrum-ts/spaces-and-users)

Inbound mapping preserves `message.sender.id`, `message.id`, reaction/reply `content.target.id`, `space.id` as `chatId`, `space.phone` as opaque `lineId` (including the SDK's `shared` value), and native timestamp milliseconds as `providerTimestamp`. Missing metadata is never invented. Outbound echoes and actor-less messages are ignored. Only incoming 👍 reactions are forwarded as possible acceptance evidence; text is relayed without interpretation. The server requires a persisted accepted current-incident send in that exact chat/line before routing wearer or responder input. The controller also matches the approved responder and persisted alert target for 👍 ownership. Conversation identifiers are omitted from public snapshots. [Official inbound shapes](https://photon.codes/docs/spectrum-ts/messages), [tapback aliases](https://photon.codes/docs/spectrum-ts/providers/imessage/messaging-features/tapback-reactions)

**Removal limitation:** inspection of the published 12.10.1 cloud source found normalization for `message.reactionAdded`, without a `reactionRemoved` arm. The adapter reports `removed:true` when explicit `reactionRecord.selected:false` or a nested reaction `unsend` is supplied, but general removal delivery is unverified. Never treat disappearance or silence as a decline. Test actual alert → 👍 on the demo phones. Use an explicit incident-coded decline to relinquish responsibility.

The listener returns a stop callback before startup succeeds, and retries connection failures or ended/failed iterators with exponential backoff from 1 to 30 seconds. Successfully handled recent message IDs are suppressed in memory across reconnections; persisted controller dedupe remains the authority across restarts. Listener diagnostics remain visible alongside outbound send status. Idle subscribed streams do not expire merely because no message arrives.

The stop callback stops dispatch/recovery, closes Spectrum once, and bounds cleanup waits. SDK initialization cannot be forcibly cancelled; a late client is stopped when it resolves. Incomplete teardown blocks replacement clients and reports unavailable recovery. SDK startup and send calls have bounded waits; a timed-out send may still complete remotely, so an unknown action must not be blindly resent. SDK telemetry is disabled.

Actionable alerts and phase updates include the exact acceptance/decline, departure, arrival, and resolution commands appropriate to that phase. Context-only handoffs do not repeat acceptance instructions. Responder questions must come from an eligible contacted phone for the active incident. Explicit stale/foreign targets or incident codes cannot fall through to a question about a newer incident.

Constrained case-insensitive progress phrases include `on it`/`I can help`, `leaving`/`on my way`, `arrived`/`I'm here`, and `decline`/`I can't help`. Each needs a current persisted message target or one exact full current incident code, plus matching chat/line. Targeted acceptance still requires an alert; departure/arrival require the assigned owner and a permitted phase. Resolution requires that on-scene owner and a concrete outcome, using `RESOLVED <id> <outcome>` or a correlated `resolved: <outcome>`. This parser is deterministic; ambiguous text never authorizes progress. Responder reports retain original text and provider time in the local audit.

Replies enter the same persisted outbox as responder alerts, retaining their original inbound target/chat/line for native threading across restarts. Generation occurs outside the transaction; only a current-version answer commits with the inbound ID and audit event. Generation interrupted before that commit requires inbound redelivery; it is not a durable generation job. Each distinct question queues separately, duplicates commit once, pre-submission failures retry, and unknown sends require reconciliation. Authorization is checked again before submission; phase changes, decline, or closure invalidate old answers. Actual reply receipt and the sourced live question/answer still need demo-phone validation. Group coordination, edited status bubbles, and miniapps are not implemented in this adapter.

## FinchNode and grounded responses

The [workshop-grounded patient-data plan](device-and-record-migration.md) supplies context for the implemented synthetic snapshot model and the separate future Connect integration.

Read `https://api.finchnode.com/demo/v1/users/patient-demo-001/records?categories=demographics,medications,conditions,allergies,vitals` without a key. Require synthetic/demo provenance. `PatientRecordSnapshot` normalizes source records, IDs/codes, prescription/administration/dispense sections, historical vitals, consent, sync metadata, category states, and warnings. Its content revision excludes local fetch time. The fixed fictional subject is not a real wearer/EHR connection. [Official demo reference](https://finchnode.com/docs/api/demo)

The first clinical context bound to an incident is persisted in SQLite with its revision and source IDs, including an unavailable result. Handoffs and responder Q&A use that immutable context across restarts. Refreshing the dashboard's patient record affects future incident context, not an existing incident's snapshot. The old eight-context process cache remains only a compatibility fallback for contexts without a structured snapshot.

Fixture consent/synchronization and category outcomes are simulated; demo category outcomes are not a production authorization contract. Local fetch time, clinical measurement date, source update, and sync time remain distinct. Vitals are historical measurements, never current incident vital signs. A prescription does not establish medication ingestion; administration and dispensing are separate dated records. Empty categories say “no records returned”; missing/revoked/out-of-scope data stays explicit. Lookup failures return unavailable and never block escalation.

JSON reads are capped at 1 MB before parsing. Returned records require valid source IDs, category labels, and typed displayed fields; malformed nested values invalidate the context. Identical aliases are deduplicated, while conflicting reuse of an ID is rejected. Unknown fields are not exposed to the model.

The model receives incident context (when present) and allowlisted synthetic record fields, then generates a schema-constrained plan: known source record IDs and fields in relevance order, selected incident facts, and explicit unavailable information. Application code renders those source values and IDs. A selected absent record field says “not returned; unknown.” Unknown IDs, field names, invalid plans, omitted available handoff categories, and omitted explicitly requested record categories visibly degrade to templates. Treatment and diagnosis questions receive an explicit limitation. Models have no tools to mutate phase, assign ownership, clear a check-in, or send messages.

Focused record questions render only relevant missing-data notices: an allergy question does not acquire unrelated location, current vital signs, or responder ETA. Explicit mixed questions retain the corresponding requested unknowns; absent fields on selected clinical records remain visible. General arrival handoffs retain their broader context and limitations.

The console pairs recorded responder questions with their persisted answer and delivery result. Each answer records its own provenance: validated AI output, degraded template, or policy refusal. `buildHandoffDetailed` likewise returns individual `ai`/`degraded` provenance and the clinical revision; the controller persists it with `HANDOFF_PREPARED`, independently of global provider status. Older entries without provenance remain explicitly unavailable. **Local AI rehearsal** uses the displayed incident's bound records, including after closure, without creating messages or incident events. Patient-record questions also work before any incident through `answerPatientQuestionDetailed`, checked against the displayed record revision.

Authenticated care-brief export separates the read-only synthetic hospital-record snapshot from local LIFELINE observations, source-labelled responder reports, and the summary's revision/provenance. Reported arrival/outcomes are not clinical diagnoses or hospital EHR entries. Export is a local JSON artifact; Finch write-back and hospital submission are not implemented.

## ElevenLabs

Set `ELEVENLABS_API_KEY` in the private `.env`, then run `npm run prepare:wili:elevenlabs`. The preparer generates seven fixed incident prompts with `eleven_multilingual_v2`, converts them to canonical 8 kHz mono PCM16 WAV files, and records voice, speed, source and checksums in the cache manifest. Default board delivery speed is 0.85. A matching complete cache avoids new provider generations; failed preparation preserves prior assets without silently switching providers. [Official conversion API](https://elevenlabs.io/docs/api-reference/text-to-speech/convert)

The stock bridge uploads and verifies board assets, then plays prompts as the incident changes. Board volume defaults to 6/10. Acceleration reporting pauses during playback and resumes before the bounded six-second microphone window; the resulting measurement gap remains visible. Local Whisper processes the transient microphone audio, and the console records the final transcript and decision. The wearer confirmed clear ElevenLabs playback, and a live microphone rehearsal recognized “I need help.” Spoken text cannot clear an incident; explicit controls remain required. The communication iPhone does not capture or play audio. See [board setup](../native/freewili/README.md) for cache preparation and playback details.

Offline tests inject fetch/SDK clients and make no real sends or speech/model generations. The public Finch fixture, local AI generation and ElevenLabs board voice have been exercised. Both approved Photon recipients are registered and both earlier connection messages have native delivery evidence; the wearer also confirmed receipt. A fresh native, no-retry diagnostic on 2026-10-03 revealed a new-contact reply cap: two of three required wearer inbound messages had arrived and replies were limited to ten until another response. After the third wearer text, a new threaded reply was sent and delivered with native send error code zero. Complete the same onboarding for the responder; do not replay previous unknown outbox actions. The Swiss responder's verified native service is RCS, while the wearer uses iMessage. The completed incident exchange remains unverified. [Official troubleshooting](https://photon.codes/docs/spectrum-ts/troubleshooting/imessage), [conversation guidance](https://photon.codes/docs/best-practices/imessage-deliverability)
