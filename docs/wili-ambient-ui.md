# WILi ambient communication

The original WILi's 320×240 screen uses five primitives: a wearer pulse, expanding connection rings, voice bars, a blue message bubble and a responder avatar. The screens use the stock firmware's image API. No firmware flash, location inference or incident-policy change is involved.

`python3 scripts/prepare-wili-ui.py` builds content-addressed RGB565 `.FWI` files in `output/wili-ui`, a contact sheet, and a standalone interactive preview in `output/wili-ui-preview`. Serve that preview with `python3 -m http.server 8892 --bind 127.0.0.1 --directory output/wili-ui-preview`. Its fictional Maya sequence never contacts the backend or records audio.

The foreground stock bridge loads generated screens automatically when `output/wili-ui/manifest.json` exists. Use `--ui-dir` for another generated directory or `--no-ui` to retain text presentation. At startup it caches at most one configured responder display name in a private temporary directory; phone numbers and transcripts are excluded. An uncached name uses generic responder art. The compact hardware set is limited to 44 unique images to leave room for audio on the OG display filesystem. Rebuild assets and restart the bridge to change artwork. Image installation runs before sensor and microphone streams start; it removes obsolete content-addressed LIFELINE images, never unrelated device files. Uploads are checked by readback rather than trusting the SDK success response alone.

The worker prepares one private image bundle for the inherited `LIFELINE_DISPATCH_MODE` (`live` by default, or `simulated`), recorded as `dispatchMode` in its manifest. It does not install both vocabularies. Product screens use the same unbadged LIFELINE artwork in both modes; dispatch provenance remains in incident and manifest metadata. Idle remains calm and silent in both modes. The backend's explicit `incident.context.dispatchMode` controls presentation; the worker never infers simulation from prose. A context that requires the other image mode immediately replaces old artwork with the current status text, without disabling later matching images. Wellbeing processing also uses text if the available image would incorrectly imply a simulated incident. The compact simulated bundle with one named responder still contains 44 unique images.

For a one-phone rehearsal, press **Yellow** when no incident is active and the received context explicitly selects simulated dispatch. This sends an operator rehearsal request with new null incident/check-in identifiers; the backend begins CHECKIN, preserving prompt → real microphone → transcript → configured wearer communication → simulated Maya dispatch. Yellow never pretends motion detected a fall and does nothing in live mode or before the first explicit simulated context. Red still requests help immediately, while Green closes only the current check-in. Yellow must be released before another press; a Yellow button held at startup or across an audio transfer is not recovered as a rehearsal. A simultaneous Red press takes precedence. The worker starts no prompt or microphone merely because Yellow was pressed; it waits for the server's correlated CHECKIN context. Simulated dispatch uses the demo responder rather than contacting a real responder; whether the wearer channel is real follows the backend's separately configured transport.

| Actual event | Screen |
| --- | --- |
| No active incident | Here with you; hold-blue hint only when wellbeing voice is enabled |
| Detected / confirming | Concentric check-in pulse; green and red controls |
| Microphone enabled | Listening bars from validated PCM RMS; quiet samples yield quiet bars |
| Bounded recording awaiting recognition | Processing dots |
| Correlated successful recognition | I heard you; a brief blue bubble, then the current phase |
| Help requested | Reaching out; abstract pulses, without map or distance |
| Responder acknowledges | Arriving bubble becomes actual responder initials |
| Responder explicitly confirms departure | On the way |
| Responder speech playback command accepted | Speaker identity and levels measured from the prepared WAV |
| Responder explicitly confirms on-scene | Two connected dots |
| Explicit resolution / check-in closure | Distinct complete/closed screens, then the ready screen after three seconds |
| Wellbeing recording reaches its bound | Release to finish; does not continue to claim listening |

Recognition acknowledges a transcript; it does **not** prove that Photon delivered an iMessage. The display therefore does not say “Sent.” Likewise, playback command acceptance and the known clip duration do not prove physical audibility. Responded, on the way, on scene and complete remain separate backend states.

All display commands execute on the existing serial-owning worker. PCM callbacks update only the presentation model. The image client suppresses commands during file transfer and near a recording deadline, limits updates to five per second, and reduces animation to one update per second when a command takes over 150 ms. Failed image commands restore the existing text presentation. Sensor gaps during existing audio playback remain real gaps.

Dynamic responder-audio upload temporarily suspends button events because the stock SDK's binary transfer consumes response/event frames. The screen says **PREPARING MESSAGE · HOLD RED FOR HELP**. Actual button levels are read before and after transfer; a newly held red press is recovered once after already queued context updates, using the current incident identity. An already-held button does not generate a new event, and a held blue button does not start unsolicited wellbeing recording. Button events resume before playback, including on upload failure; a stalled transfer closes acquisition after its finite watchdog. The SDK provides current levels rather than latched press history, so a tap pressed and released entirely during upload is unavailable. This mitigation has offline tests; it does not establish physical recovery timing or remove that short-tap limitation.

The ready image is drawn again after stock button/sensor setup. Held frames are reasserted at most once every two seconds so a stock screen redraw does not leave the UI hidden indefinitely; transfer and capture-deadline guards still apply. Asset preparation selects the board virtual environment by its environment prefix, because resolving Python executable symlinks can incorrectly select the host's different Pillow rasterizer.

The stock SDK prepends its Ctrl-B parser reset to every command, including each animation frame. `StockDisplaySerial` keeps the SDK image command and response handling, but suppresses that reset between consecutive successful image calls. Other SDK commands, image failures, and reopened connections restore the normal reset before the next image. On OG v54, a bounded hardware check accepted 16 consecutive images with resets only on the initial image, an intervening button read, and its subsequent image resynchronization. This removes repeated menu resets from the animation loop; it does not imply a documented firmware display-lock API.

Physical button press and release edges also invalidate the cached screen. The serial-owning loop then resynchronizes once and redraws the current LIFELINE image (or labelled text fallback), even if the animation frame has not changed. Repeated held levels do not cause menu resets. Restoration waits for an active file transfer or a near microphone deadline to finish; it adds no sound and never resets incident state. Red remains immediate help, and Yellow remains the simulated check-in trigger. The foreground bridge must be running and USB connected for this automatic recovery.

On the connected OG v54, the display command uses the filename only, `show_gui_image("NAME.FWI")`, matching the manufacturer's [Python hardware test](https://github.com/freewili/freewili-python/blob/master/tests/test_hw.py). Filesystem upload/readback paths remain separate from GUI-loader arguments. The wearer confirmed the actual LIFELINE screen after this correction; the earlier absolute-path success response did not establish physical rendering. The builder prefers the installed board Python runtime so preview and private contact assets use the same font rasterizer.

Setup clock pings are discarded until the worker reports ready, so a first installation cannot accumulate obsolete commands in its bounded input queue. Clock exchange resumes with fresh pings after setup. Earlier sessions observed roughly 1 Hz acceleration at rest. Full continuous startup and paired sensing after the confirmed image fix still require verification; a displayed image is not a physical fall or microphone trial.

Offline validation: `python3 native/freewili/ambient_ui_test.py`, `node --test src/stock-worker.test.ts native/freewili/stock-recovery.test.ts native/freewili/wellbeing-audio.test.ts native/freewili/conversation-audio.test.ts`, and `npm run typecheck`. The native `.FWI` format is also compared against the installed official SDK converter. Physical interaction and speaker audibility still require observation on the device.
